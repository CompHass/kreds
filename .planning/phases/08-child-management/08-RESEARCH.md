# Phase 8: Child Management - Research

**Researched:** 2026-07-01
**Domain:** Next.js App Router layout refactor, reversible AES-256-GCM encryption, Radix Dialog/AlertDialog, React Hook Form + Zod with native color input, Drizzle column migration on a populated table

## Summary

Phase 8 is mostly composition of patterns this codebase already has, plus three genuinely new pieces: (1) the project's first modal/dialog (Radix), (2) the project's first reversible (non-hash) encryption of sensitive data, and (3) the project's first shared route-group layout extraction. None of these are exotic — Node's built-in `crypto` module fully covers AES-256-GCM without new dependencies, Radix's current unified `radix-ui` package (v1.6.1) covers the dialog need, and Next.js App Router layouts are a first-class primitive for exactly the sidebar/topbar-sharing use case D-02/D-03 describe.

The highest-risk area is the encryption column: the `child_profiles` table currently has one row in the dev database with `pin_hash` already set but no `pin_encrypted` equivalent, which confirms the new column **must be nullable** (not backfillable, since there is no way to reverse an existing bcrypt hash back into a plaintext PIN). `pinEncrypted` will only get populated the next time a guardian uses "Redefinir PIN" (D-13), which writes both fields atomically. Existing children with only `pinHash` and a NULL `pinEncrypted` remain valid — the "Mostrar/Ocultar" UI (D-12) must handle NULL gracefully (e.g., disable the button or show "PIN ainda não definido").

The second risk area is migration numbering: `drizzle/` currently has two files both named `0008_*.sql` (`0008_abandoned_scourge.sql` and `0008_quick_blue_shield.sql`). Only `0008_quick_blue_shield` is registered in `drizzle/meta/_journal.json`; `0008_abandoned_scourge.sql` is an orphaned/stale file not tracked by the journal and must not be relied upon. The next migration generated by `drizzle-kit generate` will be `0009_*`, which is safe, but this orphan file is worth flagging to the planner as a pre-existing repo inconsistency (not something Phase 8 needs to fix, but not something to copy-paste from either).

**Primary recommendation:** Use Node's built-in `crypto` module (no new dependency) for AES-256-GCM PIN encryption with a 32-byte key from `PIN_ENCRYPTION_KEY` env var (base64 or hex encoded, validated in `src/lib/env.ts` alongside the existing `CHILD_SESSION_SECRET` pattern); use the unified `radix-ui` npm package for the confirmation dialog, choosing `AlertDialog` (not plain `Dialog`) because Radix's own anatomy for `AlertDialog` maps directly onto "confirm destructive/state-changing action" (Action/Cancel), which is exactly D-14's use case; extract the shared layout as a Server Component `layout.tsx` that renders `ParentSidebar` + `ParentTopbar` around a `{children}` slot, with each page keeping its own local drawer state per D-04.

### Pattern 1: Extracting a Shared Server Component Layout Without Changing Behavior

**What:** Move `ParentSidebar` + `ParentTopbar` rendering out of `ParentPanelView` (a client component) into `src/app/family/[familyId]/layout.tsx` (a Server Component), while each page's client view keeps its own local drawer state.

**When to use:** When two or more sibling routes under the same dynamic segment need identical chrome (sidebar/topbar) but must NOT share other state (D-04 explicitly forbids sharing `GuardianProfileDrawer`/`profileOpen`).

**Key constraint discovered in this codebase:** `ParentSidebar` currently takes `guardianInitial` and `onOpenProfile` as props, and `onOpenProfile` is a callback that sets client-local state (`profileOpen`) inside `ParentPanelView`. Because `layout.tsx` is a Server Component and cannot hold `useState`, the sidebar (which needs `onOpenProfile`) cannot fully move into the Server Component layout as currently written — `ParentSidebar` is a `'use client'` component, so it CAN be rendered from a Server Component layout, but the `onOpenProfile` callback and `profileOpen` state must still live somewhere. Two viable approaches:

1. **Per-page wrapper client component** — `layout.tsx` (Server) renders a thin client wrapper (e.g. `FamilyChrome`) that owns `profileOpen` state, renders `ParentSidebar` + `ParentTopbar` + `GuardianProfileDrawer`, and passes `{children}` through. This would make the drawer shared across routes — **explicitly rejected by D-04**.
2. **Layout renders chrome without drawer; page-level views own their own drawer + trigger state, and pass an `onOpenProfile` prop down through a client wrapper that only the layout owns for sidebar/topbar rendering, while each page's view independently renders its OWN copy of `GuardianProfileDrawer`.** This matches D-04's explicit instruction ("cada página mantém seu próprio drawer e estado local, replicando o padrão"). Concretely: `layout.tsx` renders a small client component (e.g. `ParentChrome`) that owns ONLY `profileOpen`+sidebar+topbar+ITS OWN drawer instance — meaning each navigation between `/tasks` and `/children` fully remounts `ParentChrome`, so there is no cross-page state leakage, and each route effectively gets a fresh, independent drawer. This is consistent with D-04 despite the drawer JSX now living in one shared client component, because the state is not lifted above the layout boundary in a way that persists across pages — Next.js layouts persist across navigations WITHIN the same layout boundary though, so this needs verification (see Pitfall 1 below).

**Example (Server Component layout wrapping a client chrome component):**
```typescript
// src/app/family/[familyId]/layout.tsx
// Source: Next.js App Router docs pattern (Server Component layout + client child)
import { auth } from '../../../auth'
import { redirect } from 'next/navigation'
import { ParentChrome } from '@/components/parent/parent-chrome'

export default async function FamilyLayout({
  children,
  params,
}: {
  children: React.ReactNode
  params: Promise<{ familyId: string }>
}) {
  const { familyId } = await params
  const session = await auth()
  if (!session) redirect('/login')

  return (
    <ParentChrome
      familyId={familyId}
      currentUserName={session.user?.name ?? ''}
      guardianEmail={session.user?.email ?? ''}
    >
      {children}
    </ParentChrome>
  )
}
```

### Pattern 2: AES-256-GCM Reversible Encryption for a Short String (Node built-in `crypto`)

**What:** Encrypt/decrypt a 4-digit PIN reversibly, isolated from the bcrypt hash used for auth.
**When to use:** Only for the "Mostrar/Ocultar" admin-reveal feature (D-12) — never for authentication.

**Example:**
```typescript
// src/lib/crypto/pin-cipher.ts
// Source: Node.js official crypto docs (nodejs.org/api/crypto.html)
import 'server-only'
import { createCipheriv, createDecipheriv, randomBytes } from 'node:crypto'

const ALGORITHM = 'aes-256-gcm'
const IV_LENGTH = 12 // bytes — recommended for GCM (96-bit nonce)
const AUTH_TAG_LENGTH = 16 // bytes (128 bits) — must match on decrypt

function getKey(): Buffer {
  const raw = process.env.PIN_ENCRYPTION_KEY
  if (!raw) throw new Error('PIN_ENCRYPTION_KEY is not set')
  const key = Buffer.from(raw, 'base64')
  if (key.length !== 32) {
    throw new Error('PIN_ENCRYPTION_KEY must decode to exactly 32 bytes (256 bits)')
  }
  return key
}

// Output format: base64(iv) + ':' + base64(authTag) + ':' + base64(ciphertext)
export function encryptPin(pin: string): string {
  const key = getKey()
  const iv = randomBytes(IV_LENGTH)
  const cipher = createCipheriv(ALGORITHM, key, iv, { authTagLength: AUTH_TAG_LENGTH })
  const ciphertext = Buffer.concat([cipher.update(pin, 'utf8'), cipher.final()])
  const authTag = cipher.getAuthTag()
  return [iv, authTag, ciphertext].map((b) => b.toString('base64')).join(':')
}

export function decryptPin(stored: string): string {
  const key = getKey()
  const [ivB64, tagB64, ctB64] = stored.split(':')
  const iv = Buffer.from(ivB64, 'base64')
  const authTag = Buffer.from(tagB64, 'base64')
  const ciphertext = Buffer.from(ctB64, 'base64')
  const decipher = createDecipheriv(ALGORITHM, key, iv, { authTagLength: AUTH_TAG_LENGTH })
  decipher.setAuthTag(authTag)
  const plaintext = Buffer.concat([decipher.update(ciphertext), decipher.final()])
  return plaintext.toString('utf8')
}
```


### Pattern 4: `<input type="color">` bound to React Hook Form + Zod

**What:** Native browser color picker as a controlled RHF field.
**Example:**
```typescript
// Source: React Hook Form + @hookform/resolvers Zod integration docs
import { useForm } from 'react-hook-form'
import { zodResolver } from '@hookform/resolvers/zod'
import { z } from 'zod'

const CreateChildSchema = z.object({
  displayName: z.string().min(1, 'Nome obrigatório'),

  // ...

```
`<input type="color">` always yields a valid 7-char lowercase hex string (`#rrggbb`) from the browser's native picker — the Zod regex is a defense-in-depth check for direct API calls bypassing the UI, not something the picker itself can violate.

### Anti-Patterns to Avoid
- **Using `pinEncrypted` for any authentication check:** D-11 is explicit — `child-guard.ts` and `verifyChildPin` must never read or compare against `pinEncrypted`. Only `pinHash` (bcrypt) is used for login.
- **Backfilling `pinEncrypted` for existing children:** There is no way to recover a plaintext PIN from an existing bcrypt hash. Do not attempt a data migration that "fills in" `pinEncrypted` for the one existing child row — it must stay NULL until the guardian explicitly resets that child's PIN.
- **Reusing an IV across encryptions with the same key:** Always generate a fresh `randomBytes(12)` IV per `encryptPin` call (Node crypto docs pitfall — reusing an IV with GCM catastrophically breaks confidentiality).
- **Sharing `GuardianProfileDrawer` state across `/tasks` and `/children`:** Explicitly rejected in D-04/Deferred Ideas — keep drawer state page-local even after the layout refactor.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Focus trap + ESC-to-close for the confirmation dialog | Custom `useEffect` keydown listener + manual `tabindex` cycling | Radix `AlertDialog` (`radix-ui` package) | Radix's `FocusScope`/`DismissableLayer` primitives already handle focus trapping, ESC dismissal, and scroll locking correctly across browsers — reimplementing this is a well-known accessibility footgun |
| AES-GCM encrypt/decrypt | A hand-rolled XOR cipher or a naive `crypto.createCipher` (deprecated legacy API) | Node's `createCipheriv`/`createDecipheriv` with `aes-256-gcm` | `createCipher` (no `iv`) is deprecated and insecure (derives IV from password directly); `createCipheriv` with explicit random IV is the documented correct API |
| Form validation for the add-child panel | Manual `if` checks scattered through `onChange` handlers (as `TaskFormPanel` currently does) | `react-hook-form` + `zodResolver` | Already a project dependency per CLAUDE.md; this phase is the natural place to start actually using it since `TaskFormPanel`'s raw-`useState` pattern was arguably a stack deviation in Phase 5 |

**Key insight:** The three "don't hand-roll" items above are exactly the three genuinely new capabilities this phase introduces (dialog, encryption, form library usage) — reusing established primitives here is what keeps a small greenfield-feeling phase from becoming its own multi-week source of subtle bugs.

## Common Pitfalls

### Pitfall 1: Next.js layout persistence across sibling routes may leak `ParentChrome` client state between `/tasks` and `/children`
**What goes wrong:** In App Router, a shared `layout.tsx` component instance is preserved (not remounted) when navigating between sibling routes that share the same layout segment. If `ParentChrome` (or whatever client wrapper renders the drawer) holds `profileOpen` state, navigating from `/tasks` to `/children` will NOT reset that state, meaning the drawer could stay open across the navigation — which looks like "sharing" even though D-04 says each page should have independent state.
**Why it happens:** App Router intentionally preserves layout state across navigations for UX continuity (this is a feature, not a bug, for things like scroll position or persistent UI). But D-04 wants independence.
**How to avoid:** Do NOT put `profileOpen`/drawer state in the shared `layout.tsx`'s client wrapper. Keep `GuardianProfileDrawer` + its `open` state declared inside each page's own root client component (`ParentPanelView` for `/tasks`, `ChildrenPanelView` for `/children`), exactly as D-04 specifies, and pass `onOpenProfile` down as a prop from the page's view into `ParentSidebar`/`ParentTopbar` — which means `ParentSidebar`/`ParentTopbar` themselves CAN live in the shared layout (they're stateless/prop-driven), but the drawer and its open/close state must NOT.
**Warning signs:** Drawer stays open after clicking a sidebar nav link to switch routes; drawer content briefly shows stale guardian data during navigation.

### Pitfall 2: `ParentSidebar`/`ParentTopbar` currently receive `onOpenProfile` as a plain callback prop — but if they move into `layout.tsx` (Server Component), that callback must originate from a client boundary
**What goes wrong:** A Server Component cannot define `() => setProfileOpen(true)`. If `ParentSidebar` moves into `layout.tsx` directly, there's no client state to wire `onOpenProfile` to at that level.
**Why it happens:** Server/Client component boundary — event handlers can only be defined in Client Components.
**How to avoid:** Two working options: (a) `layout.tsx` (Server) renders children as-is but does NOT own `ParentSidebar`; instead, each page's client view renders sidebar+topbar+drawer as it does today, and the "layout" is really just the auth-gate + data-fetching Server wrapper — meaning "shared layout" in this codebase means "shared auth check," not "shared JSX component instance" — OR (b) create a thin client wrapper rendered BY the layout (e.g. `ParentChrome`) that owns sidebar/topbar/drawer state, accepting the Pitfall 1 tradeoff and explicitly re-deriving/resetting drawer state via a `key={pathname}` remount trick if cross-page independence must be preserved. Given D-04's explicit language ("cada página mantém seu próprio drawer e estado local"), option (a)-adjacent (sidebar+topbar move to a client component instantiated once per page, imported by both `/tasks` and `/children`, NOT literally placed inside `layout.tsx`'s Server Component tree with shared state) is the safer reading — but D-02 explicitly says the layout.tsx should contain `ParentSidebar` + `ParentTopbar`. **This is a genuine ambiguity the planner must resolve** — see Open Questions.
**Warning signs:** TypeScript error "onClick is not a valid prop in a Server Component" or a build failure citing event handlers passed to Server Components.

### Pitfall 3: `AlertDialog.Action` closes the dialog immediately on click, before an async Server Action resolves
**What goes wrong:** If `onConfirm` is `async` (calls a Server Action and awaits the DB write), Radix's `AlertDialog.Action` still fires its own `onOpenChange(false)` synchronously on click — the dialog closes immediately regardless of whether the async operation has completed. For an optimistic-UI pattern (matching `handleToggle` in `parent-panel-view.tsx`), this is fine — but if the UI needs to show a loading/pending state INSIDE the dialog before closing, the default `Action` behavior will close too early.
**Why it happens:** Radix's `AlertDialog.Action` is designed for the common "fire and close" case, not a "wait then close" case.
**How to avoid:** Since this project's established pattern is optimistic UI + fire-and-forget Server Action calls with `.catch()` logging (see `handleToggle` in `parent-panel-view.tsx`), the default immediate-close behavior is actually consistent with existing conventions — call the Server Action inside `onConfirm` without awaiting in the click handler (or await it but don't gate the dialog's close on it), matching `toggleTaskActive`'s fire-and-forget style.
**Warning signs:** Dialog flickers closed while a network request is still pending; a "reactivate" action appears to succeed in the UI before the DB write actually lands.

### Pitfall 4: Env var validation for `PIN_ENCRYPTION_KEY` must fail fast at startup, not at first PIN-reveal request
**What goes wrong:** If `PIN_ENCRYPTION_KEY` is missing or malformed, and the only place it's read is inside `encryptPin`/`decryptPin`, the failure only surfaces the first time a guardian tries to set or reveal a PIN — potentially in production, long after deploy.
**Why it happens:** Lazy env var access defers validation to first use.
**How to avoid:** Add `PIN_ENCRYPTION_KEY` to the existing `envSchema` in `src/lib/env.ts` (parsed eagerly at module load, same as `CHILD_SESSION_SECRET`), so a missing/malformed key fails the build/boot immediately rather than at request time.
**Warning signs:** 500 errors only on "Redefinir PIN" or "Mostrar" actions in production while everything else works fine.

### Pitfall 5: The orphaned `0008_abandoned_scourge.sql` migration file
**What goes wrong:** Two files in `drizzle/` are both named `0008_*.sql`. Only `0008_quick_blue_shield.sql` is registered in `drizzle/meta/_journal.json` (idx 8). `0008_abandoned_scourge.sql` is NOT in the journal and appears to be a stale/orphaned file (likely from a discarded `drizzle-kit generate` run that was regenerated). If a future `drizzle-kit generate` run were pointed at a stale `meta/` snapshot, or if someone manually renames files, this could cause confusion about migration order.
**Why it happens:** Pre-existing repo state, not something Phase 8 introduced.
**How to avoid:** Phase 8's new migration will be auto-numbered `0009_*` by `drizzle-kit generate` (journal's next `idx` is 9), which is unaffected by the orphan file. Do not manually copy or reference `0008_abandoned_scourge.sql`. Optionally flag for cleanup (deletion) in a later phase, but out of scope for Phase 8's plan.
**Warning signs:** none expected for Phase 8 itself — purely a "don't be confused by this file" note.

### Pitfall 6: Existing `child_profiles` row already has `pin_hash` set with no corresponding "reversible" PIN available
**What goes wrong:** The one seeded child ("Ana") already has a bcrypt `pinHash`. There is no way to derive the original plaintext PIN from that hash to populate `pinEncrypted` retroactively.
**Why it happens:** bcrypt is a one-way hash by design.
**How to avoid:** Design the "Mostrar/Ocultar" UI and `revealChildPin` Server Action to explicitly handle `pinEncrypted IS NULL` (e.g., render "PIN ainda não definido — use Redefinir PIN" instead of attempting to decrypt `null`). The migration must make `pin_encrypted` nullable (no `NOT NULL` constraint, no default) — confirmed necessary by the current populated-table state.
**Warning signs:** Decrypt function throws on `null` input; "Mostrar" button crashes for any child who has a PIN from before this phase shipped.

### Server Action pattern for reset-pin (mirrors `updateTask`/`createTask` conventions)
```typescript
// Source: existing src/app/actions/tasks.ts pattern, adapted
'use server'
import { auth } from '../../../auth'
import { db } from '@/lib/db'
import { childProfiles } from '@/lib/db/schema'
import { eq, and } from 'drizzle-orm'
import { revalidatePath } from 'next/cache'
import { hashPin } from '@/lib/families/child-pin'
import { encryptPin } from '@/lib/crypto/pin-cipher'
import { validatePinFormat } from '@/lib/families/child-pin'

export async function resetChildPin(childId: string, familyId: string, pin: string) {
  const session = await auth()
  if (!session) throw new Error('Unauthorized')
  if (!validatePinFormat(pin)) throw new Error('Invalid PIN format')

  const [pinHash, pinEncrypted] = await Promise.all([
    hashPin(pin),
    Promise.resolve(encryptPin(pin)), // D-13: both written together, same transaction
  ])

  await db
    .update(childProfiles)
    .set({ pinHash, pinEncrypted, updatedAt: new Date() })
    .where(and(eq(childProfiles.id, childId), eq(childProfiles.familyId, familyId)))

  revalidatePath(`/family/${familyId}/children`)
}
```

## Open Questions

1. **Does D-02's "layout.tsx contendo ParentSidebar + ParentTopbar" mean literal JSX composition inside the Server Component, or a client wrapper instantiated per-layout?**
   - What we know: D-02 says the layout should contain both components; D-04 says drawer state must stay page-local (not lifted to the shared layout).
   - What's unclear: `ParentSidebar`/`ParentTopbar` are `'use client'` components that currently receive an `onOpenProfile` callback tied to page-local `profileOpen` state. Rendering them directly from `layout.tsx` (Server Component) is technically legal (Server Components CAN render Client Components and pass them serializable+function props are actually NOT serializable across the server/client boundary unless the function is itself defined in a Client Component) — meaning `onOpenProfile` cannot be defined inline in `layout.tsx`. The layout would need to receive `children` and somehow also let each page inject its own `onOpenProfile` — which defeats moving the sidebar out of the page.
   - Recommendation: The cleanest resolution consistent with both D-02 and D-04 is: `layout.tsx` (Server) renders `<>{children}</>` plus performs the shared `auth()` check/redirect; a NEW shared client component (e.g., `ParentShell`) is exported from `components/parent/` and is imported+rendered by EACH page's own client view (`ParentPanelView`, `ChildrenPanelView`) — i.e., "shared" means "same imported component, instantiated per-page," not "same component instance persisted by the Next.js layout tree." This avoids Pitfall 1 entirely (no cross-page state persistence) while still satisfying D-03's goal of not duplicating the sidebar/topbar JSX (it's defined once, imported twice). This interpretation should be confirmed with the user/planner before task breakdown, since it changes what "layout.tsx" actually contains (mostly just the auth guard) versus what D-02's wording implies.

2. **Should `resetChildPin` and `revealChildPin` be wrapped in a single DB transaction with the audit event table (`familyAuditEvents`)?**
   - What we know: `familyAuditEvents` schema exists but is currently unused anywhere in `src/` (dead code/infrastructure since an earlier phase).
   - What's unclear: CONTEXT.md doesn't mention audit logging for Phase 8 actions at all (not in Decisions, not in Deferred Ideas).
   - Recommendation: Treat as out of scope for Phase 8 (not mentioned = not required), but flag to the user that `familyAuditEvents` remains unused — a future phase may want to wire deactivate/PIN-reset events into it for parity with its schema's intent.

|---------------|---------|-------------------|
| V2 Authentication | Yes (indirectly — PIN reset touches auth material) | `bcrypt` (unchanged, cost factor 10) remains sole auth verification path; AES-GCM encrypted copy is explicitly NOT part of the auth path (D-11) |
| V3 Session Management | Yes (D-15 boundary) | Existing JWT (`jose`, HS256, 8h expiry) session handling in `child-session.ts`/`child-guard.ts` — unchanged this phase by explicit decision |

### Known Threat Patterns for this Stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| PIN encryption key leaked via client bundle or logs | Information Disclosure | `PIN_ENCRYPTION_KEY` read only in `server-only`-marked modules (`src/lib/crypto/pin-cipher.ts` must import `'server-only'` like `child-pin.ts` does); never pass the key or ciphertext to client components as props unless already decrypted server-side for display |
| Cross-family PIN reveal (guardian of Family A reveals Family B's child PIN) | Elevation of Privilege | `revealChildPin`/`resetChildPin`/`toggleChildActive` must filter `WHERE childProfiles.familyId = session-derived-familyId`, not a client-supplied `familyId` — matches `T-06-15`/`T-06-13` mitigations already established in Phase 6 |
| IV reuse in AES-GCM | Tampering (catastrophic key/plaintext recovery) | `randomBytes(12)` fresh per encryption call, never a static/derived IV |
| Deactivated child's still-valid JWT used to access data after deactivation | Elevation of Privilege (accepted risk per D-15) | Explicitly accepted tradeoff — documented in CONTEXT.md; do not "fix" this in Phase 8 by modifying `child-guard.ts` |
| CSRF on children Route Handlers | Tampering | Next.js Server Actions have built-in Origin header CSRF protection (already noted in `tasks.ts`); Route Handlers under `/api/family/[familyId]/children/*` should mirror the same `auth()` session check as `tasks/route.ts` |
