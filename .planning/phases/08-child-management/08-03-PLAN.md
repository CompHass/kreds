<objective>
Build the child-management backend: the `ChildProfileView` type + Zod schemas in `src/types/child.ts`, the four Server Actions (`createChild`, `resetChildPin`, `revealChildPin`, `toggleChildActive`) in `src/app/actions/children.ts`, and the Route Handlers under `src/app/api/family/[familyId]/children/`. Every action/handler is auth-guarded and familyId-scoped. `resetChildPin` dual-writes bcrypt `pinHash` + AES-GCM `pinEncrypted` (D-13); `revealChildPin` decrypts server-side and returns null for pre-existing NULL-encrypted rows (Pitfall 6). `toggleChildActive` soft-deactivates without touching `child-guard.ts`; a Wave-0 unit test extension proves the D-15 boundary (a deactivated child's still-valid JWT continues to pass the unchanged guard, so deactivation only blocks the NEXT login, never the live session).

Purpose: This is the contract layer consumed by the Plan 05 `ChildrenPanelView`. Defining these signatures and Zod schemas first lets Plan 04 UI components and Plan 05 integration build against fixed interfaces without a scavenger hunt. The D-15 boundary test is what makes the "no change to child-guard.ts" decision safe to rely on downstream.
Output: types, actions, route handlers, the Wave 0 PIN-reset integration test, and the D-15 guard-boundary unit test extension.
</objective>

| Boundary | Description |
|----------|-------------|
| client → Server Action | guardian-submitted child data + PIN reset requests |
| client → Route Handler | JSON body for list/create/patch under /api/family/[familyId]/children |
| server → DB | dual-write of bcrypt hash + AES-GCM ciphertext |
| deactivated child ↔ live JWT | a session issued before deactivation survives until natural 8h expiry (D-15 accepted risk) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-05 | Elevation of Privilege | cross-family child access (reveal/reset/toggle Family B's child) | mitigate | every mutation/read scoped by `and(eq(childProfiles.id, childId), eq(childProfiles.familyId, familyId))`; familyId from session/URL never body (mirrors T-06-15); integration test asserts cross-family reset is a no-op |
| T-08-08 | Spoofing | unauthenticated action/handler call | mitigate | `await auth()` guard on every Server Action (throw Unauthorized) and Route Handler (401) |
| T-08-09 | Information Disclosure | plaintext PIN leaking to client on list fetch | mitigate | ChildProfileView exposes only hasEncryptedPin boolean; plaintext returned ONLY by explicit revealChildPin call |
| T-08-10 | Tampering | client-supplied familyId in request body | mitigate | familyId injected from URL params in Route Handlers; body familyId ignored |
| T-08-11 | Repudiation/auth-confusion | pinEncrypted used for authentication | mitigate | children.ts never imports child-guard/verifyPin; auth path stays bcrypt-only (D-11) |
| T-08-13 | Elevation of Privilege | deactivated child's still-valid JWT used until expiry | accept | D-15 accepted risk (CONTEXT.md line 129); Task 4 unit test documents the boundary and asserts the guard is intentionally unchanged; new-login rejection deferred to `verifyChildPin` DB query, out of scope this phase |
| T-08-SC | Tampering | npm installs | accept | this plan installs no packages |
