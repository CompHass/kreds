<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| Browser to Next.js auth/onboarding | Untrusted user input and session cookies enter server-side auth and family creation. |
| Next.js to ZITADEL | External IdP assertions are trusted only after Auth.js validation and verified email gate. |
| Next.js to PostgreSQL | Family-scoped commands must constrain every read/write by membership and family_id. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|---|---|---|---|
| T-02-01 | Spoofing | `auth.ts`, `src/lib/auth/session.ts` | mitigate | Validate Auth.js ZITADEL session, require stable `sub`, and require verified email when claim is present. |
| T-02-02 | Tampering | `createFamilyForGuardian` transaction | mitigate | Create family, identity, membership, and audit event in one Drizzle transaction; rollback on any failure. |
| T-02-03 | Information Disclosure | `/api/families`, `src/app/page.tsx` | mitigate | Remove all-family enumeration and require membership-filtered family_id queries. |
| T-02-04 | Elevation of Privilege | `family_memberships.role` | mitigate | Store Kreds `guardian`/`child` roles in domain table and never infer family role solely from ZITADEL claims. |
| T-02-05 | Repudiation | `family_audit_events` | mitigate | Write sanitized parent-readable audit event for family creation and membership creation. |
| T-02-SC | Tampering | npm installs | mitigate | Install only `next-auth@5.0.0-beta.31` after confirming research slopcheck OK; no unvetted auth packages. |
</threat_model>
