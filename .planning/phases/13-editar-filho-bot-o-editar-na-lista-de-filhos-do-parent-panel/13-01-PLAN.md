<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| formData (client) → updateChildAction (server) | Untrusted form input crosses into a Server Action; childProfileId, displayName, ageYears, avatarPreset, accentColor are all attacker-controllable strings before parsing |
| updateChildAction → updateChildProfile | familyId and guardianIdentityId passed to updateChildProfile come from the server-resolved session/membership (not from formData), preventing cross-family forgery via a spoofed familyId in the request body |
| updateChildProfile → childProfiles row | childProfileId from formData could reference a profile in a different family or an inactive profile; updateChildProfile's existing WHERE clause (childProfileId AND familyId) and active-check already reject both cases with a thrown Error |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13-01 | Tampering | updateChildAction — childProfileId from formData | mitigate | updateChildProfile's WHERE (childProfileId AND familyId) query, unchanged by this plan, ensures a childProfileId belonging to another family returns "Child profile not found or not in this family" and no row is updated — familyId itself is never taken from formData, only from the server-resolved membership |
| T-13-02 | Tampering | updateChildAction — guardianIdentityId | mitigate | guardianIdentityId is always resolved server-side via resolveKredsIdentityId(identity.zitadelSub) from the authenticated session, never read from formData — same pattern as addChildAction/deactivateChildAction, no new attack surface introduced |
| T-13-03 | Elevation of Privilege | updateChildProfile — inactive profile bypass | mitigate | Existing `if (!existing.active) throw new Error('Cannot update a deactivated child profile')` check (unchanged by this plan) already blocks mutation of deactivated profiles; ageYears extension does not alter this guard |
| T-13-04 | Tampering | updateChildProfile — ageYears out-of-range | mitigate | New validation in Task 1 rejects ageYears outside 0-120 or non-integer before any DB write, mirroring createChildProfile's existing D-09 constraint |
| T-13-SC | Tampering | npm/pip/cargo installs | accept | No new package installed in this plan — only existing modules (child-profiles.ts, actions.ts) are extended |
</threat_model>
