<objective>
Fix a privilege-escalation gap (PR6): a child's `child-session` cookie coexists with a
guardian's next-auth session cookie on the same device. After a child logs in with a PIN,
the child can navigate to `/family/[familyId]/...` or `/guardian/*` (guardian panels) because
the `/family/*` + `/guardian/*` middleware branch only checks for the presence of the next-auth
cookie and falls straight through when it is present.

Purpose: Enforce that an active child session cannot reach guardian-scoped routes, even when a
valid guardian cookie is also present on the device. Also give guardians a way to exit the
child profile (clear the `child-session` cookie) to reclaim the device without re-authenticating
via Zitadel.

Output:
- `src/middleware.ts` guards `/family/*` and `/guardian/*` against a valid child-session JWT.
- New `exitChildProfile` server action in `src/app/actions/child-auth.ts`.
- UI trigger in the child garden view (client component) to call the action.
- Extended `tests/unit/middleware.test.ts` covering the new guard.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-PR6-01 | Elevation of Privilege | /family/* + /guardian/* middleware branch | mitigate | Verify child-session JWT with `jwtVerify` (CHILD_SESSION_SECRET) BEFORE the next-auth presence check; a verified `role=child` token forces redirect to /family/access/{familyId} even when a next-auth cookie is present. |
| T-PR6-02 | Spoofing / Tampering | forged or expired child-session cookie | accept-then-mitigate | `jwtVerify` in try/catch — unverifiable tokens are never trusted and never block a guardian; they fall through to the existing next-auth check. No payload field is read from an unverified token (CR-02 precedent). |
| T-PR6-03 | Repudiation | exitChildProfile action | accept | Cookie deletion is a local device action with no financial/ledger effect; no audit trail required for this quick fix. |
